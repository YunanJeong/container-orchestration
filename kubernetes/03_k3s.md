# K3s

## Installation

- [요구사항(포트, 메모리 등)](https://docs.k3s.io/installation/requirements)
- [K3s 시작, 설치](https://docs.k3s.io/quick-start)

### K3s Server 설치 (Controlplane+Node)

K3s Server는 쿠버네티스 컨트롤플레인과 노드(워커)가 한 세트로 설치된다. 노드 1개일 땐 이 Server만 설치하면 됨

```sh
# 설치 시 옵션 적용 예시
# INSTALL_K3S_VERSION   : 설치할 버전 지정(생략시 최신 버전). (버전 목록: https://github.com/k3s-io/k3s/releases)
# sh -s -               : stdin 파이프로 받은 쉘스크립트 실행. 뒤에 주입할 옵션이 없을시 "sh -" 로 기술가능
# --docker              : 컨테이너 런타임을 기설치된 docker로 지정하여 설치 (생략 시 기본 containerd)
curl -sfL https://get.k3s.io | INSTALL_K3S_VERSION={version} sh -s - --docker

# ---  개별 작성법 예시

# 기본 설치 (최신 버전, 기본 런타임 containerd로 설치)
curl -sfL https://get.k3s.io | sh -

# 특정 버전 설치
curl -sfL https://get.k3s.io | INSTALL_K3S_VERSION={version} sh -

# 컨테이너 런타임을 도커로 지정하며 설치
curl -sfL https://get.k3s.io | sh -s - --docker
```

### 설치 후 설정

```sh
# k3s context파일(k3s.yaml)을 표준경로(~/.kube/config)로 옮겨준다.
# 표준경로에 기존 context가 있다면, 수동으로 텍스트 편집하여 k3s 추가 
# context 파일의 소유자, 소유그룹이 실제 작업 user와 일치하면서 `chmod 600`을 하면 warning, permission denied 없이 사용가능
mkdir -p ~/.kube
sudo cat /etc/rancher/k3s/k3s.yaml > ~/.kube/config
# sudo chown myuser:myuser ~/.kube/config  # 파일 소유자&소유그룹 변경
sudo chmod 600 ~/.kube/config

# kubectl 설정
echo 'export KUBECONFIG=~/.kube/config' >> ~/.bashrc
echo 'alias k="kubectl"' >> ~/.bashrc
source ~/.bashrc
```

- k3s 독자 경로인 `/etc/rancher/k3s/k3s.yaml`를 써도 되지만, 단일 kubectl로 여러 클러스터 컨텍스트를 관리시 비권장 

### 리셋

```sh
# 설정 및 클러스터 리셋
sudo systemctl stop k3s
sudo rm -rf /var/lib/rancher/k3s/
sudo systemctl start k3s
```

### 삭제 [[참고]](https://docs.k3s.io/installation/uninstall)

```sh
# k3s-server 삭제
/usr/local/bin/k3s-uninstall.sh

# k3s-agent 삭제
/usr/local/bin/k3s-agent-uninstall.sh
```

## 클러스터 확장 (노드 추가)

기존 클러스터에 노드를 붙이는 방법은 둘이다. 무엇을 늘리느냐가 다르다.

- k3s-agent 추가: 노드(워커)만 늘린다. (컨트롤플레인은 그대로)
- k3s-server 추가: 컨트롤플레인 + 노드(워커)를 함께 늘린다. (컨트롤플레인 HA용)

### K3s Agent 추가 (노드만 늘리기)

Agent는 워커 노드만 추가한다 (컨트롤플레인 아님).

```sh
# K3s Agent 설치
# agent           : Agent(워커 노드)로 설치함을 명시 (K3S_URL이 있으면 생략 가능)
# K3S_URL         : join할 Server의 주소 (이 변수가 있으면 설치 스크립트가 Agent로 인식)
# K3S_TOKEN       : join에 필요한 토큰 (Server에서 조회: sudo cat /var/lib/rancher/k3s/server/node-token)
# --docker        : 컨테이너 런타임을 기설치된 docker로 지정하여 설치 (생략 시 기본 containerd)
export K3S_URL=https://{k3s_server_ip}:6443
export K3S_TOKEN={k3s_server_token}
curl -sfL https://get.k3s.io | sh -s - agent --docker

# 환경변수를 export 없이 한 줄로 입력
curl -sfL https://get.k3s.io | K3S_URL=https://{k3s_server_ip}:6443 K3S_TOKEN={k3s_server_token} sh -s - agent --docker

# 설치 완료 후 Server측에서 연결 확인
kubectl get nodes
```

### K3s Server 추가 (컨트롤플레인+노드 늘리기)

컨트롤플레인 HA는 k3s-server를 여러 대 두어 구성한다. k3s-server는 컨트롤플레인+노드 한 세트라 컨트롤플레인만 따로 설치할 수 없고, k3s-server를 늘리면 워커 노드도 그만큼 늘어난다.

단, k3s는 경량화를 위해 쿠버네티스 상태 저장소(데이터스토어)로 SQLite를 기본 사용하는데, 이것으로는 HA 구성이 불가하다. 따라서 첫 번째 server 설치 때부터 `--cluster-init`으로 데이터스토어를 etcd(일반 쿠버네티스의 기본 저장소)로 활성화해야 한다.

```sh
# 1번째 Server 설치
# server          : Server(컨트롤플레인+노드)로 설치함을 명시 (K3S_URL이 없으면 생략 가능, default가 server모드)
# --cluster-init  : 데이터스토어를 기본 SQLite 대신 etcd로 시작 (다중 Server HA의 기반. 첫 Server에만 사용)
# --docker        : 컨테이너 런타임을 기설치된 docker로 지정하여 설치 (생략 시 기본 containerd)
curl -sfL https://get.k3s.io | sh -s - server --cluster-init --docker
```

```sh
# 2번째 이후 Server 설치 (1번째 Server에 join)
# --server        : join할 기존 Server 주소 (join 시점에만 쓰임. 살아있는 Server면 아무거나 OK, join 후엔 이 노드에 안 묶임)
# K3S_TOKEN       : join에 필요한 토큰 (기존 Server에서 조회: sudo cat /var/lib/rancher/k3s/server/node-token)
export K3S_TOKEN={k3s_server_token}
curl -sfL https://get.k3s.io | sh -s - server --server https://{k3s_server_ip}:6443 --docker

# 환경변수를 export 없이 한 줄로 입력
curl -sfL https://get.k3s.io | K3S_TOKEN={k3s_server_token} sh -s - server --server https://{k3s_server_ip}:6443 --docker

# 설치 후 확인 (ROLES 컬럼에 control-plane,etcd,master 표시된 노드가 Server = 컨트롤플레인)
kubectl get nodes
```


## 컨트롤플레인 HA 구성

단일 K3s Server는 컨트롤플레인이 SPOF(단일 장애점)다. 그 노드가 죽으면 클러스터 관리 기능(API·스케줄링)이 마비된다. 프로덕션·상시 운영이면 K3s Server를 여러 대로 두어 컨트롤플레인을 이중화(HA)한다.

### 왜 하는가

- 컨트롤플레인이 1대면 그 노드가 죽을 때 클러스터 관리(API·스케줄링)가 마비된다 = SPOF.
- 여러 대로 두면 1대가 죽어도 나머지가 관리 기능을 이어받아 유지된다.

### 구성 방법

- K3s의 경우, 첫 Server를 `--cluster-init`으로 시작하면 etcd 모드가 켜지고, 이후 추가 Server를 `--server`로 join한다.
- 과반(쿼럼) 확보를 위해 홀수(3, 5 …)로 구성한다.
- K3s Server는 controlplane + 워커를 겸한다 (K3s는 기본 taint가 없어 Server 노드에도 앱이 스케줄됨).

### 쿼럼 (과반 합의 정족수, etcd 동작 원리)

- etcd는 과반(쿼럼) 합의 구조다. 쿼럼 = (전체/2)+1.
- 과반을 확보한 쪽만 동작하고, `과반을 못 넘기면 스스로 멈춘다`
  - => `네트워크가 갈라져도 양쪽이 각자 다른 데이터를 쓰는 사태(split-brain)를 원천 차단.`
  - => 개별 클러스터로 나뉘어 동작하는게 아니라 정지되는 것이므로 복구시 정상화됨
- 그래서 홀수가 효율적이다. 짝수는 대수만 더 쓰고 견디는 장애 수는 같다.

| 전체 Server | 쿼럼 | 견디는 장애 |
|:---:|:---:|:---:|
| 1 | 1 | 0대 (SPOF) |
| 3 | 2 | 1대 |
| 5 | 3 | 2대 |
| 2 | 2 | 0대 (1대만 죽어도 정지 → 오히려 취약) |

- 2대 구성은 피한다. 1대만 죽어도 과반(2) 미달로 멈춰서, 단일보다도 장애 내성이 없다.
- etcd는 멤버 목록을 명시적으로 기록하고, 쿼럼도 이 멤버 수 기준으로 계산한다.
  - 정상 절차로 제거하면 멤버에서 빠져 쿼럼도 재계산되지만, 장애로 죽은 노드는 자동으로 빠지지 않는다 → 전체 멤버 수가 그대로라 쿼럼 정족수도 그대로다.
  - 그래서 죽은 채 방치하면 살아있는 대수만 줄어 "지금은 돌지만 장애 내성 0"인 상태가 된다. (`kubectl get nodes` 목록과는 별개 계층)

### 장단점 (트레이드오프)

- 얻는 것: 컨트롤플레인 1대 장애를 견딤 (3대 기준).
- 감수하는 것:
  - 쿼럼 규율 — 홀수 유지. 1대 죽으면 방치 말고 빨리 복원.
  - 디스크 속도 — etcd는 쓰기 지연(fsync)에 민감. Server 노드는 SSD/NVMe 권장. (용량은 작음)
  - etcd 스냅샷 백업 — 최악(데이터 소실) 대비.
- 리소스 오버헤드 자체는 작다. 소규모 클러스터 기준 노드당 수백 MB~1~2GB 메모리, 0.x코어 수준이라 8코어/32GB급 노드면 무시할 만하다.

### 장애 시 동작

- `컨트롤플레인 마비 ≠ 워크로드(Pod) 정지. 쿼럼이 깨져 컨트롤플레인이 멈춰도, 이미 떠 있는 파드는 각 노드의 kubelet이 계속 실행`한다. 멈추는 것은 관리 기능(새 배포·스케줄링·조회·죽은 파드 자가복구)이다.
- 3대 중 2대가 죽으면 쿼럼(2) 붕괴 → API는 read-only로 잠기지만, 데이터와 실행 중 파드는 살아있다. 치명적 데이터 손실이 아니다.
- 단, 이 상태에서 추가 장애가 나면 방치되므로(자가복구 정지) 빨리 복구해야 한다.

### 복구

- 1대 죽음 (쿼럼 유지): 죽은 노드의 etcd 데이터가 멀쩡한 채 되살아나면 자동으로 재합류해 쿼럼이 회복된다. 대부분의 장애(재부팅·일시 단절)는 그냥 되살리면 복구됨.
- 2대 죽음 (쿼럼 붕괴): 데이터·IP가 유지된 채 되살리면 복구된다. 데이터가 소실됐다면 살아남은 1대에서 `k3s server --cluster-reset`으로 단일 etcd로 강제 재구성한 뒤(필요 시 스냅샷 복원), 다시 Server를 join해 홀수로 채운다.
- 죽은 멤버 영구 제거: `kubectl delete node`는 쿠버네티스 노드 오브젝트만 지우며 etcd 멤버는 빠지지 않는다(별개 계층). etcd 멤버 제거는 `etcdctl member remove`로 별도 수행해야 쿼럼이 재계산된다. (K3s는 etcdctl을 기본 포함하지 않으므로 별도 설치 + K3s의 etcd 인증서·엔드포인트 지정 필요)

> ⚠️ `--cluster-reset`은 "데이터를 보존한 채 etcd를 단일 멤버로 되살리는 복구"다. 위 `### 리셋` 섹션의 `rm -rf`는 "데이터를 지우고 처음부터 재생성하는 초기화"로, 이름은 비슷하나 성격이 정반대다.

### 평상시 관리

- 패치: 한 대씩 롤링(무중단) 또는 통째로 graceful 재부팅(간단). graceful stop이면 재기동 시 쿼럼이 복구되므로, 소규모에선 통째 재부팅이 실무적으로 유효하다. (정상 종료 + 데이터 디스크 보존이 전제면 데이터·복구는 안전하고 무중단만 포기하는 셈)
- 롤링 규율: 한 번에 1대만, 복귀(노드 Ready + etcd 멤버 healthy) 확인 후 다음 대.
- 1대 죽은 취약 상태를 오래 두지 말고 홀수로 복원.
- etcd 스냅샷 자동 백업을 켜둔다.

## 클러스터 구성시 필요한 내부 네트워크 인가[[참조]](https://docs.k3s.io/installation/requirements#inbound-rules-for-k3s-nodes)

- K8s 배포판 및 설정마다 조금씩 다름
- 여기선 K3s default 기준으로 최소 필요목록을 기술함
- 아래 포트를 모든 노드 간 방화벽 허용하면 됨
- **6443**
  - K8s API Server
  - kubectl이 controlplane에 접근하기 위한 용도
- **10250**
  - K8s kubelet metrics
  - metrics 모니터링
- **8472**
  - K8s Pod-to-Pod
  - **UDP**
  - 클러스터 내부 Pod, ClusterIP 간 통신 허용
  - 노드를 넘나드는 트래픽이 있을 때 노드 간에 내부적으로 실제 사용되는 포트
- **30000-32767**
  - K8s NodePort
  - 클러스터 내부에서 NodeIP:NodePort로 통신시 허용
  - 클러스터 구성에 필수는 아니지만, 초기설정해놓으면 편리
  - 원래 클러스터 내부 통신용 IP:Port로는 ServiceName(ClusterIP):ServicePort를 쓰는 것이 정석이고, 이 때 물리적 노드를 건너가는 트래픽의 경우 UDP 8472포트가 사용된다. 하지만 특정 앱 구현에 따라 실제 서버의 NodeIP:NodePort로 통신하는 경우가 있다.
    - (e.g. bitnami/kafka에서 advertised.listeners로 통신시 실제 서버IP:Port를 이용하도록 설계됨)

## 클라우드(AWS EC2) 클러스터 구축 사례 (EKS 아님)

- 조건에 따라 다양한 네트워크 구성방법이 있겠으나, 일반적으로 다음과 같이 하는게 편하다.

### 클러스터 내부 통신

- 클러스터 내부 통신은 Private IP로 한다.
- 단일 VPC 내에 모든 노드가 있다면, `자기참조하는 보안그룹`을 생성하여 모든 노드에 등록한다. 자기참조 보안그룹이 등록된 노드들끼리는 전체 포트에 대하여 Private IP로 상호통신할 수 있다.
- 이후 클러스터 구성시 각 노드에서 K8s API server(:6443)를 가리키는 주소를 Private IP로 설정하면 된다.
- 개별 보안규칙을 자세히 설정할 수도 있겠으나, 향후 스케일링 등 유지보수 상황에서 매우 번거로워질 수 있기 때문에 지양한다.
- Public으로 클러스터 구성시 더 느리고, 비용들고, 보안적으로 좋지 않음

### 클러스터 외부 통신

- 소규모 클러스터
  - 각 노드에 할당된 Public IP를 이용
  - 모든 노드가 공유하는 공통보안그룹 사용할 것
- 대규모 or 스케일링이 잦은 클러스터
  - AWS NAT와 AWS LoadBalancer(LB)를 활용
    - `외부시스템과 연결시 IP기반 상호 인증/인가 등이 필요한데, 노드마다 이를 처리하기는 번거롭다. 큰 서비스 단위로 단일지점을 제공할 필요`가 있음.
    - 또한 직결되는 Public IP가 노출되지 않으므로 보안적으로도 더 우수
  - 인바운드
    - 외부시스템(Public) => `AWS LB(Public IP, DNS)` => 클러스터(Private IP)
    - EKS가 아니므로 LB 자동생성은 불가
    - AWS LB 수동 생성 후 K8s에서 LoadBalancer Service 배포시 LB 주소와 메타데이터를 적절히 입력하면 연동된다.
    - LB에는 개별 보안그룹 설정필요
    - `LB 단에서 SSL/TLS 인증 처리가 가능`함. ACM(AWS Certificate Manager) 활용시 무료발급/자동갱신까지 된다! 이렇게 하면 클러스터 내부에 배포되는 App. 레벨에서 인증서를 신경쓰지 않아도 된다.
  - 아웃바운드
    - 클러스터(Private IP) => `AWS NAT(Public IP)` => 외부시스템(Public)
    - NAT 개별 생성 후 연동

## 온프레미스 클러스터 구축 사례(K3s)

### 시작하기전에

- k3s에서 Pod 간 네트워크는 CNI(Container Network Interface) 표준을 기반으로 flannel이 대표적으로 활용되며, flannel은 VXLAN(Virtual eXtensible LAN) 오버레이 기술을 사용해
노드 간 물리적 네트워크 위에 가상 네트워크 터널을 만든 뒤, Pod들의 트래픽을 8472/UDP 터널 포트로 캡슐화해 각 노드 간 안전하게 전달한다.
- NIC(Network Interface Controller, 네트워크 인터페이스)
  - `ifconfig`했을 때 나오는 각 항목
- CNI(Container Network Interface)
  - CNCF에서 관리하는 컨테이너 통신을 위한 네트워크 표준 규격
- VXLAN
  - vpn과 비슷한 구조
- Flannel
  - K3s에서 default로 채택한 CNI 도구

### 인프라 환경

- 서버 7대
- eth0: 기본 사설망 IP
- eth1: 고대역폭망 IP
- 고대역폭이 필요한 시스템으로, 별도 망에 추가로 연결되었다.
- 각 서버마다 `다중 IP가 할당`된 상황이며, `별도 설정이 없을시 K3s는 기본 사설망(eth0)을 default로 선택`한다.
- 이를 `고대역폭망 IP(eth1)로 변경`하여 클러스터 내외부 트래픽이 송수신되도록 해야 함

### 설정 필요한 부분

- 각 노드에서 가리키는 K3s Api Server의 주소를 eth1로 설정(:6443에 관여)
- 각 노드의 internal ip를 eth1로 설정(:8472, :10250에 관여)
  - 각 노드가 클러스터 내부에서 자기자신을 인식하는 주소를 의미
  - 노드마다 다르게 실제 eth1으로 할당된 주소를 설정해줘야 함
- flannel의 NIC를 eth1로 설정(:8472에 관여)
  - 앞 과정에서 internal ip를 설정했음에도 불구하고 flannel이 eth0으로 트래픽전송 시도함
  - eth1을 수동선택 해줘야 함
- external ip
  - Service 리소스 배포시 eth1의 IP로 설정

### 설정방법

- k3s server, agent 설치단계에서 옵션설정으로 가능

```sh
# 설치 시 설정
curl -sfL https://get.k3s.io | sh -s - --docker --node-ip x.x.x.x --flannel-iface=eth1
```

- 이미 설치된 경우, systemd 서비스파일을 수정하는 방식으로도 변경가능
- 실행 명령어에서 옵션 추가 후 daemon-reload와 restart
  - /etc/systemd/systemd/k3s.service
  - /etc/systemd/systemd/k3s-agent.service
  - 그래도 신규설정이 반영되지 않을 수 있는데, 이 때는 각 논리적 노드를 삭제(kubectl delete node)하고 재등록해준다. 재등록은 서비스 restart하면 됨.

```service
# 서비스 파일 내 수정 할 부분
ExecStart=/usr/local/bin/k3s server --docker --node-ip x.x.x.x --flannel-iface=eth1
```

### 트러블 슈팅을 위한 기타 명령어

```sh
# 모든 NIC에 대해 8472 udp 포트 패킷 캡처
sudo tcpdump -i any udp port 8472 -vv

# NIC 'eth1'의 8472 udp 포트 패킷 캡처
sudo tcpdump -i eth1 udp port 8472 -vv

# internal ip 확인
kubectl get nodes -o wide

# 인증서 만료 확인
openssl s_client -connect localhost:6443 -showcerts < /dev/null 2>&1 | openssl x509 -noout -enddate 

# 인증서 정보 확인(k3s 구버전 미지원)
sudo k3s certificate check
```
